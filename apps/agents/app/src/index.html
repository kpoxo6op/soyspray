Earning trust in coding agents

A study guide to Lauren Tan’s talk on letting coding agents land changes you review afterwards, and on what has to be true before you can.

Her answer is trust earned with evidence: agents that verify their own work, skills grown from watching agents fail, and checks that make the easy change the correct one.

Terms you’ll meet

In the order the talk introduces them. Each time opens that moment of the recording.

Trust curve
Her informal picture of moving from watching every agent step to letting agents work unattended.
Parallelism is gated by how much evidence you have that output is correct.
Auto-merge
Changes land without prior human approval.
She reviews after landing; only advisable behind hard checks.
Verification
The agent checks its work by running the real app.
Real execution, traces, profiling or simulation; yields correct, not necessarily good, code.
Control skill
Lets an agent drive and inspect the running app.
Uses debugging protocols such as Chrome DevTools Protocol, or Apple simulator tooling.
Feature map
A guide telling agents where each feature is and how to reach it.
Location, navigation, shortcuts and selector attributes for each feature.
pstack
Tan’s plugin of skills, named partly as a joke.
Includes skills for creating and maintaining verification setups and an eval playbook, per the talk.
Skill
A written instruction file an agent loads for a type of task.
Mostly markdown encoding context and procedure; born from observed failures.
Eval
A test of whether an agent with a skill behaves as intended.
Unit tests for agents; rubric, sub-agents, multiple models, independent judge.
Judge agent
A second agent that scores the first one’s work.
She uses a different model to reduce bias.
Git worktree
An extra working folder on the same repository.
Lets parallel agents edit without overwriting each other.
Cloud agent
An agent working on a remote machine.
Can act on signals such as bug reports without you present.
Dune
Code name for the agent-oriented architecture behind Grok Bot.
Conventional feature directories plus CI bans on known-bad patterns.
Main and renderer process
The two halves of an Electron app; the renderer draws the UI.
Heavy work in the renderer causes stutter; CI blocks crossing imports.
Hard versus soft enforcement
Checks that block versus advice that can be ignored.
CI, lint and compiler errors block; rules, skills and review bots can be forgotten.

The offline lab

Rehearse every control in a scratch Git repository: deterministic stub agents, no network, no credentials.

Python 3 and Git · about 50 minutes · one folder you choose

  1. 1Get the script

    Download lab.py into a directory of its own, outside any repository, and read it before running it. It uses only the Python standard library, opens no network connection and never runs a shell string. It does not look for credentials because it needs none.

    Download lab.py

  2. 2Run it

    Choose a lab root whose parent already exists and which does not exist yet, for example ~/agent-lab. The script refuses your home directory itself and the filesystem root.

    python3 -I lab.py run --root ~/agent-lab

    Before writing anything, the script checks the root and every parent for symlinks and for Git repositories that have a remote. Only then does it create the root with mode 0700 and an ownership marker that records the path and your user ID.

  3. 3Read the output

    The run prints one line per control, then a JSON summary in which offline is true and seven steps are listed. Each line below says what it proved and how to check it yourself.

    1. PREFLIGHT: owned root; no symlinks or Git remotes; stub agents only

      Preflight and ownership5 min · Worktree

      Create an owned, disposable lab root that the script refuses to leave.

      What happens, how to check it, how it transfers

      The failure it rehearses

      Point --root at a new folder inside a clone that has a remote, or at your home directory. The script prints STOP and creates nothing. Point it at an existing folder it did not create, and it also stops, because the ownership marker is missing.

      In your cluster

      Equivalent to a fresh, uncredentialed workspace; agents never get your kube context or registry tokens.

      Lesson 1

    2. WORKTREES: git worktree add; independent edits; git merge reports a conflict

      Shared tree versus worktrees8 min · Worktree

      Results entryCONFLICT-SURFACED: config.txt

      What happens, how to check it, how it transfers
      1. The script creates two worktrees, wt-a and wt-b, on branches agent-a and agent-b. Each stub agent commits a different greeting to config.txt.
      2. It merges agent-a into main, then attempts agent-b. Git reports a conflict on config.txt. The script confirms that config.txt is the only unmerged file, then aborts the merge.
      3. It resets main to the initial commit, so later exercises start from the verified baseline rather than from either agent’s greeting.

      Check it yourself

      git -C ~/agent-lab/repo worktree list
git -C ~/agent-lab/repo log --oneline --all

      The failure it rehearses

      Contrast this with a shared tree. If both stubs had written config.txt in one directory, the second write would have replaced the first with no error. Worktrees turn that silent loss into a conflict a reviewer must resolve.

      In your cluster

      Each Soyspray agent task gets its own worktree and branch; conflicts surface at PR review.

      Lesson 6 · Experiment: Two agents, one file

    3. VERIFICATION: sh check.sh proves PASS on baseline and FAIL on a known-bad branch

      A check that runs the real thing8 min · Verify

      Results entryPASS baseline; REJECT claimed but wrong change

      What happens, how to check it, how it transfers
      1. The script commits check.sh, which runs app.sh and passes only if the printed value is hi.
      2. Known-good case: on main, sh check.sh prints PASS.
      3. Known-bad case: on branch agent-c, a stub agent changes the greeting and writes a commit message claiming the fix is done. On that branch check.sh prints nothing and exits 1, and the script requires that failure.
      4. The script switches back to main.

      Expected

      The agent-c commit message claims a fix, but its config.txt reads greeting=hey.

      Check it yourself

      git -C ~/agent-lab/repo log --oneline -1 agent-c
git -C ~/agent-lab/repo show agent-c:config.txt
(cd ~/agent-lab/repo && sh check.sh)

      The failure it rehearses

      This one is built in. If check.sh ever passed on agent-c, the run would stop with STOP. A check that cannot fail on a known-bad change proves nothing.

      In your cluster

      Soyspray CI and harness checks are the probe; require their output, not an agent’s claim.

      Lesson 2 · Experiment: Done, or verified?

    4. FEATURE MAP: check listed paths exist; billing.sh is the known stale entry

      A checkable feature map6 min · Agent

      Results entrySTALE: billing.sh; real paths exist

      What happens, how to check it, how it transfers
      1. The script writes feature-map.txt with three entries, each mapping a feature name to a path: greeting to config.txt, app to app.sh, and billing to billing.sh.
      2. It checks every listed path. Known-good: config.txt and app.sh exist. Known-bad: billing.sh is deliberately missing, and the script requires exactly that one stale entry.
      3. The map stays untracked, so it never enters a commit.

      Check it yourself

      cat ~/agent-lab/repo/feature-map.txt
git -C ~/agent-lab/repo status --short

      In your cluster

      A Soyspray map from app name to apps/NAME/app, manifests and checks, validated in CI.

      Lesson 3

    5. BOUNDARY: execute check-boundary.py; allowed import passes, shortcut fails

      Make the shortcut fail8 min · Checks

      Results entryPASS allowed path; BLOCKED shortcut import

      What happens, how to check it, how it transfers
      1. The script creates main/heavy.sh and renderer/view.sh, then writes check-boundary.py, which fails if any renderer script refers to main/.
      2. Known-good case: while the renderer only draws, the check prints PASS-boundary and exits 0.
      3. Known-bad case: the stub agent takes the shortcut and makes the renderer source the main script. The check prints FAIL-boundary and exits 1, and the script requires that failure.

      Check it yourself

      cat ~/agent-lab/repo/renderer/view.sh

      The failure it rehearses

      Imagine replacing the check with a README sentence asking agents not to import main: nothing would stop the shortcut. The script deliberately does not include that soft-rule version.

      In your cluster

      Equivalent to Soyspray’s policy gates: non-root, read-only, no egress, enforced rather than requested.

      Lesson 5 · Experiment: The shortcut import

    6. RETRY: atomic mkdir claims/R7 succeeds once; repeated claim is skipped

      Claim tasks atomically6 min · Claim

      Results entryclaimed:R7 then skip:R7; one claim

      What happens, how to check it, how it transfers
      1. The script creates claims/ in the lab root, then claims report R7 by creating the directory claims/R7. Creating a directory either succeeds or fails as one operation, so only one delivery can win.
      2. A second delivery of R7 tries to create the same directory, fails because it already exists, and is skipped. If that second claim ever succeeded, the script would stop with STOP.
      3. No branch or worktree is opened for R7; the exercise isolates the claim itself.

      Check it yourself

      ls ~/agent-lab/claims

      In your cluster

      Key agent work by report or issue ID and claim it atomically before any agent starts; a re-sent signal must not open a second PR.

      Lesson 6 · Experiment: Retry without a claim

    7. PROMOTION: git diff main promote -- contains only promotion.json

      Rehearse the promotion boundary8 min · Promote

      Results entrypromotion.json only; source main unchanged

      What happens, how to check it, how it transfers
      1. The script creates branch promote from main and commits only promotion.json, which records a stub image digest and that human approval is required.
      2. It returns to main and confirms that promotion.json is the only file that differs between main and promote. Source and activation never travel together.
      3. The run writes results.json in the lab root, then runs verify itself. No step contacts a model, registry, cluster or remote.

      Check it yourself

      git -C ~/agent-lab/repo diff --name-only main promote --

      In your cluster

      Source PR, then CI builds the image, then a separate digest promotion PR, then Argo. No agent pushes, merges a promotion or touches the cluster.

      Lesson 6 · Lesson 7

  4. 4Verify and clean up

    python3 -I lab.py verify --root ~/agent-lab

    Verify rechecks ownership, the seven recorded steps, check.sh PASS on main and the promotion-only diff, then prints the same seven-step summary.

    python3 -I lab.py cleanup --root ~/agent-lab

    Cleanup rechecks the ownership marker, deletes only that root and prints that it removed the owned lab root. Then delete lab.py yourself.

  5. 5If it prints STOP

    A refusal prints a line starting with STOP: on stderr, exits with status 1 and creates nothing. That is the lab working: it found a symlink, a repository with a remote, a missing ownership marker or a location it will not touch.
